# Outcome status

- [x] Landing page and runtime: Node.js 18+ with Express serves a single ABC Company landing page, plain browser JavaScript without a framework or build step, and starts after `npm install` with `npm start`. The browser only receives the public LaunchDarkly client-side ID, never server SDK keys, provider keys, or trigger URL. Dependencies remain small: Express, dotenv, LaunchDarkly SDKs, one LLM client, and `jose` for signed sessions.
- [ ] Live release and remediation verification: The implementation wraps the chat widget with boolean `release-support-chat`; on shows and off hides it. A LaunchDarkly change listener is wired to switch without reload. The panel shows the value and timestamped changes. README gives dashboard trigger steps and a ready-to-edit curl POST; `npm run kill-switch` reads the trigger URL from `.env` and handles missing or failed requests. **Live flag changes and the real trigger require account configuration and have not been observed from this no-credential environment.**
- [ ] Live targeting verification: The switch-user control offers five sample contexts with key, name, email, plan (free/pro/enterprise), region (us/eu), role (admin/member), and boolean betaTester. It calls `identify` and re-evaluates without reload; the active attributes are displayed. README gives exact individual targeting for Alex and rule targeting for `plan = enterprise` and `betaTester = true`. **The no-key UI switch was exercised, but account-backed re-evaluation has not been observed.**
- [ ] Live AI Config verification: The chat endpoint evaluates an AgentControl config for model and prompt, then the AI SDK calls OpenAI. The key comes from `.env` or injected environment. Without a provider key it returns a labeled canned reply. Each reply reports variation, model, and prompt template. README documents two variations. **The canned path passed tests; live AI output needs a configured account and provider key.**
- [x] Repository handoff: The public GitHub repository contains README instructions for the exact flag, trigger, AgentControl config, SDK-key locations and scope, and local startup. `.env.example` lists inputs; `.env` is ignored, with no keys committed. Code comments explain LaunchDarkly calls. README/comments contain no em dashes. A clean source copy passed `npm install`, startup, route checks, and tests on Node 22 and Node 18.
- [x] Continuous integration: The public GitHub repository contains a credential-free GitHub Actions workflow for Node 18 and 22, smoke tests, syntax checks, and production-dependency audit. Both hosted jobs passed in [run 37358836777](https://github.com/derekuzzle/abc-company-launchdarkly-demo/actions/runs/37358836777). The workflow pins Node 24-based actions and Ubuntu 24.04 for future runs.
- [x] Server-side flag enforcement: Before evaluating the AI Config or calling OpenAI, the Express chat endpoint evaluates the exact `release-support-chat` boolean for the selected synthetic sample context with the server SDK and the same environment key. It denies globally off or non-targeted contexts; missing credentials, initialization failure, or evaluation errors fail closed. Browser widget visibility alone is never authorization. An emergency runtime switch independently denies requests if the SDK has cached a stale On value. Tests exercise the real server SDK using LaunchDarkly's offline TestData source; live account behavior remains unverified below.
- [x] Chat access protection: Only explicitly allowlisted Manus-authenticated users may call `/api/chat`. Login binds OAuth state to a one-use browser nonce, exchanges the code on the server, and keeps the app session in a signed HttpOnly cookie. Cross-origin POSTs, missing/expired sessions and non-allowlisted identities cannot reach AI. The five sample contexts remain illustrative targeting choices, not authentication identities. Mocked OAuth/session tests pass; the actual hosted redirect remains in the live deployment outcome.
- [x] Rate limiting and cost control: Chat attempts are bounded per allowed email and connecting socket peer in a rolling window, concurrent AI requests per caller are capped, and login initiation is rate-limited. Excess returns 429 with `Retry-After`; tests cover count and concurrency. Limits and one-use OAuth nonces are process-local; the socket peer may be a shared platform proxy. Only a single instance is supported for a login flow until a distributed nonce store and trusted ingress limits are added.
- [ ] Live deployment: Configure keys and allowed origin/email through protected runtime settings, verify Login, flag On/Off, rule targeting, kill switch, AI Config variations and model/prompt metadata in the deployed application. Do not claim live access or AI verification before account-backed tests pass.
